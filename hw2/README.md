# HW2. Парсер Funny: LL(1), рекурсивный спуск

Парсер написан руками на Python. Он берёт токены от лексера из HW1 (его ДКА), строит AST в JSON и восстанавливается
после ошибок (режим паники).

## Запуск

Из папки `hw2/`, нужен [uv](https://docs.astral.sh/uv/). `hw1` подключается автоматически как локальная зависимость.

```bash
uv run hw2 tests/good/step04_good_nested_if.funny
```

```bash
uv run hw2 lex tests/good/step01_good_basic.funny
```

```bash
uv run hw2 test
```

- `hw2 файл.funny` — как компилятор: печатает AST в JSON, а если есть ошибки, то список
  `файл:строка:столбец: сообщение` и код возврата 1.
- `lex` — токены с позициями.
- `test` — прогоняет `tests/good` (сравнивает AST с эталоном `.json`) и `tests/bad` (сравнивает ошибки с `.txt`).

## Код

| Файл | Что делает |
|---|---|
| `src/hw2/lexer.py` | лексер с позициями поверх ДКА из HW1 |
| `src/hw2/parser.py` | рекурсивный спуск: одна функция на правило грамматики, построение AST, режим паники |
| `src/hw2/__init__.py` | команды `parse` / `lex` / `test` |

## Грамматика

Полная грамматика — в `grammar.txt`, каждое правило там — одна функция в `parser.py`.

**Приоритеты** (от слабого к сильному):

| Оператор | Ассоциативность |
|---|---|
| `->` | правая: `a -> b -> c` = `a -> (b -> c)` |
| `or` | левая |
| `and` | левая |
| `not` | унарный |
| `== != < <= > >=` | нет: `a < b < c` — ошибка |
| `+ -` | левая: `a - b - c` = `(a - b) - c` |
| `* /` | левая |
| `-` (унарный) | унарный |

**Как приведено к LL(1):**

- левая рекурсия в выражениях заменена циклами по уровням приоритета;
- присваивание выбирается по токену после имени: `=` — обычное, `[` — обновление массива, `,` — кортеж;
- функция и формула различаются по `=>` после `)`;
- в выражении после имени: `(` — вызов, `[` — массив, иначе — переменная;
- висячий `else` относится к ближайшему `if`.

**Отклонения от `funny.ru.md`:**

1. `condition`, `predicate` и `expr` объединены в одно правило `expr`. В исходной грамматике по `(` нельзя понять,
   начинается `(a + b) > c` или `(a > b and c)`, то есть она не LL(1). Проверка «тут нужно условие, а не число»
   (`if (r)`, `assert r`) оставлена на проверку типов в HW3.
2. Слово `function` перед функцией необязательное: в примерах курса его нет, а в P03 и HW1 оно есть.
3. Формула заканчивается `;`, как в `project/examples/step12`.
4. Импликация пишется как `->` или `→` (в примере step12 стоит `→`).

## Лексер

Используется минимальный ДКА из HW1 (`hw1.lexer.build()`), алгоритм тот же: longest match. Добавлено:

- позиции токенов (строка и столбец с 1);
- в комментарии `//...` разрешены любые символы до конца строки — в примерах курса комментарии русские;
- `→` понимается как `->`;
- в конце добавляется токен `EOF`;
- ошибки лексера: неизвестный символ выкидывается, число с ведущим нулём (`01`) сообщается, но читается как число,
  чтобы парсер мог продолжить.

## AST

Каждый узел — JSON-объект с полем `node`:

| Узел | Поля |
|---|---|
| `program` | `items` — функции и формулы |
| `function` | `name`, `params`, `requires`, `returns`, `ensures`, `uses`, `body` |
| `formula` | `name`, `params`, `body` |
| `block` | `body` — список операторов |
| `assign` | `targets` — список имён, `value` |
| `if` | `cond`, `then`, `else` |
| `while` | `cond`, `invariant`, `body` |
| `assert`, `assume` | `cond` |
| `binop` | `op` (`+ - * / == != < <= > >= and or ->`), `left`, `right` |
| `neg`, `not` | `arg` |
| `int`, `bool` | `value` |
| `var` | `name` |
| `index` | `array`, `index` |
| `call` | `name`, `args` |
| `forall`, `exists` | `var`, `body` |

- Параметры, результаты и `uses` — объекты `{"name": ..., "type": "int" | "int[]" | null}`.
- Отсутствующие `requires`, `ensures`, `else`, `invariant` — `null`.

**Обновление массива сразу обессахаривается:** `b[0] = 42;` превращается в `assign` с `targets: ["b"]` и
`value: call set(b, 0, 42)`. Для `a[i][j] = v` получается `a = set(a, i, set(a[i], j, v))`.

## Ошибки

Сообщения в формате `строка:столбец: ожидалось X, а встретилось Y`, например:

```
2:15: ожидалось ')', а встретилось '{'
```

**Режим паники.** При ошибке внутри блока парсер пропускает токены до `;` или до `}` этого оператора (вложенные
`{...}` пропускаются целиком) и продолжает со следующего оператора. Ошибка в заголовке функции пропускает функцию до
конца её тела. Каждая ошибка либо съедает хотя бы один токен, либо заканчивает текущий блок, поэтому парсер не
зацикливается. За один прогон находится несколько ошибок (см. `tests/bad/many_errors.funny`).

## Тесты

`uv run hw2 test`: **39/39 PASS**.

- `tests/good` — 24 программы `good_*` из `project/examples` курса и `extras.funny` (ключевое слово `function`,
  `uses`, кванторы, `a[i][j] = v`, `->`, пустой блок). Для каждой есть эталон AST `.json`.
- `tests/bad` — 14 программ:
  - пустой ввод и ввод из одного комментария;
  - незакрытые `{` и `(`;
  - лишние токены;
  - неверные операторы `**`, `===`, `=<`;
  - нет `returns`;
  - справа от `x, y =` не вызов;
  - ошибки лексера (`01`, `@`);
  - несколько ошибок в одном файле;
  - пример из P03 без точек с запятой;
  - мусорный ввод;
  - `bad_missing_semicolon` и `bad_missing_paren` из примеров курса.

  Для каждой есть ожидаемый список ошибок `.txt`.

Остальные `bad_*` из примеров курса синтаксически правильные: там ошибки смысла (неизвестное имя, неверное число
аргументов, `if (r)` с числом). Парсер их принимает, а ловить их — задача проверки типов в HW3.
